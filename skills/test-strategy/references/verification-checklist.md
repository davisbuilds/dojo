# Reviewing Test Evidence

Use these questions when coverage is uncertain or a test review is requested.
Select the relevant ones; this is not a required completion checklist or report.

- Could a plausible regression pass these assertions? Did the failing baseline
  exercise the intended behavior rather than a missing symbol or earlier guard?
- Is the oracle independent of the code under test? Are assertions about the
  contract, including order or interactions only where those matter?
- Does a negative result have a known positive control? Is an existing control
  sufficient, or would a targeted mutation expose a meaningful coverage gap?
- Does the dependency substitute preserve the semantics this claim needs? What
  wiring, platform, or real-service behavior remains untested?
- Could shared state, leaked resources, or unbounded waits make the result
  misleading? Are external effects authorized and isolated?
- Do results apply to the current change and relevant runtime inputs? Are
  project-required checks satisfied? Which remaining limit affects the claim?

For authority boundaries, use `authority-boundary-testing.md`: both permitted
and forbidden operations, observation outside the subject, and proof from the
effective runtime. Do not infer enforcement from generated policy alone.

## When retiring or consolidating tests

Identify what distinct failure the test detects before deciding it is redundant.
Use relevant history when its purpose is unclear, and compare the actual assertions
and execution paths with the proposed replacement. Two tests touching the same
code need not protect the same contract. Consider retaining, rewriting at the
owning boundary, or consolidating before deleting.

Static/source assertions, exact generated bytes, call order, or slow integration
checks can protect real packaging, configuration, compatibility, or authority
contracts. Keep them where that is the intended observable behavior; brittleness
or runtime alone does not establish low value. Conversely, preserve the useful
contract rather than freezing an obsolete implementation merely because it has a
test.

If cleanup also removes production code, inspect its consumers and package entry
points. A grep with no callers does not establish dead code across re-exports,
dynamic dispatch, or generated paths. Verify the affected build/runtime and any
replacement regression protection. A green suite after deleting assertions is
not, by itself, evidence that coverage survived.

Apply this only to the proposed cleanup; it requires no retirement card, deletion
quota, extra approval cycle, or whole-suite audit. A useful external example is
[gstack's test-audit retention guidance](https://github.com/garrytan/gstack/blob/f67c478f05d8e0b39339599ad11c91a3478515ae/test-audit/SKILL.md).
